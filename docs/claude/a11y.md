# /a11y — auditoria e correção de acessibilidade

## Para que serve

Revisão sistemática de acessibilidade (WCAG 2.2 AA) do markup Vue/Nuxt do projeto, com correções aplicadas diretamente (a menos que `--report` seja passado). É a versão adaptada de um comando bem maior, construído originalmente para um projeto React com design system próprio baseado em Radix UI/React Aria — nenhum dos dois existe aqui, então este comando é **modo único**: lê o markup real, confere contra WCAG, corrige o que dá para corrigir, sinaliza o que precisa de humano (contraste, tamanho real renderizado).

## Quando usar

Ao revisar acessibilidade de um componente específico, ou como varredura geral do app. Também é o comando indicado quando o passo 4 do `/check` (uma única linha de checklist) não é suficiente.

## O que ele faz (passo a passo)

1. **Escopo** — `/a11y` sozinho audita tudo em `app/components/`, `app/pages/`, `app/layouts/` e `app/error.vue`; `/a11y <caminho ou nome>` audita um arquivo específico; `--report` em qualquer chamada só reporta, sem alterar arquivos.
2. **Leitura** — lê cada arquivo-alvo por completo (nunca audita de memória, já que um achado anterior pode estar desatualizado).
3. **Checklist WCAG 2.2 AA** — teclado e foco (inclui um alerta específico: `ProfessionalFiltersSheet.vue` é o único dialog real do app e é o candidato mais provável a não mover/devolver foco corretamente), nome acessível/roles/estados ARIA, imagens, formulários, conteúdo dinâmico (`role="alert"`/`aria-live`), cor e contraste, tamanho de fonte (nota o uso de `px` em vez de `rem` como decisão a ponderar, não correção automática), motion reduzido, alvos de toque (mínimo 24×24, 44×44 em CTAs primárias). Itens hoje não aplicáveis (confirmação de ação destrutiva, dicas de formato, atalhos de teclado) ficam marcados para o futuro.
4. **Correções** (a menos que `--report`) — ordem de prioridade do nome acessível faltante até o motion reduzido faltante; usa a utility `sr-only` do Tailwind, já adotada no projeto.
5. **Testes** — como todo componente já tem teste em `test/components/` com piso de 90%, uma correção que muda comportamento (um `aria-label` novo, foco que passa a mover para dentro do dialog) deve ganhar ou atualizar uma assertion no teste existente; `npm run test:coverage` deve rodar de novo depois. Adotar `axe-core`/`vitest-axe` fica **fora** deste comando — é decisão separada, só sinalizada no relatório.
6. **Relatório** — tabela de problemas por arquivo (critério WCAG, categoria, descrição, linha), tabela de verificação manual necessária, e um resumo com contagens.

## Pré-requisitos

Nenhum — não depende de nenhuma biblioteca de acessibilidade instalada (é por isso que o modo é único, sem tabelas de mapeamento de dependência como na versão original).
