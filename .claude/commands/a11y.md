# /a11y — Accessibility audit & fix

Systematic WCAG 2.2 AA accessibility review of this app's markup, with fixes applied directly unless `--report` is passed. Adapted from a much larger `/a11y` command built for a React project with a Radix UI/React Aria-backed design system (`@zenity-ui`) and a Design-System-vs-feature-file split.

**Neither of those applies here** — DevMatch has no separate design-system package (components live directly in `app/components/`, styled with plain Tailwind + the classes in `main.css`) and no accessibility-primitive library (no Radix Vue / Headless UI / Reka UI dependency). So this is a **single mode**: read the real markup, check it against WCAG, fix what's fixable, flag what needs a human (contrast, real rendered sizes). If a dependency for accessible primitives is ever added to this project, dependency-mapping tables like Zenity's would belong back in this command.

## Invocation

- `/a11y` — audit everything under `app/components/`, `app/pages/`, `app/layouts/`, and `app/error.vue`
- `/a11y <path or component name>` — audit one file (e.g. `/a11y ProfessionalFiltersSheet` resolves to `app/components/professional/ProfessionalFiltersSheet.vue`)
- `/a11y --report` / `/a11y <path> --report` — audit without modifying files

`$ARGUMENTS` contains whatever was passed after `/a11y`.

## Step 1 — Determine scope

- Empty (or `--report` alone) → audit everything listed above.
- A bare name with no `/` or `.vue` → resolve it by searching `app/components/**` and `app/pages/**` for a matching filename; ask if more than one match.
- A path → use it directly.
- `--report` anywhere in the arguments → `REPORT_ONLY=true`; otherwise fixes are applied.

## Step 2 — Read the real markup

Read each target file in full. Don't audit from memory of what a component "probably" looks like — a prior finding in this same file can go stale the moment someone edits it.

## Step 3 — WCAG 2.2 AA checklist

### Keyboard & focus (2.1.1, 2.1.2, 2.4.3, 2.4.7)
- Every interactive element reachable via Tab/Shift+Tab.
- No `<div @click>` / `<span @click>` standing in for a control — it needs `role`, `tabindex="0"`, and `@keydown.enter`/`@keydown.space`, or (almost always simpler here) just use a real `<button>`/`<a>`/`<NuxtLink>`. This app's own convention is native elements throughout — flag any drift from that.
- No `outline-none`/`outline: none` without a visible `:focus-visible` replacement (this project already uses real `:focus` styling on most controls via browser defaults — check any place that suppresses it).
- **`ProfessionalFiltersSheet.vue` is the one real dialog in this app** (`role="dialog"`, `aria-modal="true"`, Escape closes it, body scroll is locked). Verify it also moves focus into the sheet when it opens and returns focus to the trigger button when it closes — that's the part most likely to be missing, since it's easy to get the ARIA attributes right and still skip focus management.
- No keyboard trap anywhere.

### Names, roles, values (4.1.2)
- Every interactive element has an accessible name: visible text, `aria-label`, or a wrapping `<label>` (the search input's pattern — `<label>` wrapping an `sr-only` span + the `<input>` — is correct and the one to replicate).
- Icon-only buttons (favorite toggle, sheet close button, etc.) carry `aria-label`.
- Decorative `<svg>` icons have `aria-hidden="true"` — this app has a lot of inline SVGs; check every one, not just the obvious ones.
- ARIA state matches real state: `aria-pressed` on toggle buttons (filter chips, favorite), `aria-current="page"` on the active breadcrumb crumb, `aria-expanded` on anything that opens/closes.

### Images (1.1.1)
- `<NuxtImg>`/`<img>` has a meaningful `alt` (`ProfessionalAvatar.vue`'s `Foto de ${name}` is the pattern).
- Standalone informative SVGs (none currently — all are decorative) would need `role="img"` + `aria-label` if one is added.

### Forms (1.3.1, 3.3.1, 3.3.2)
- Inputs associated with a label (via wrapping `<label>`, `for`/`id`, or `aria-label`/`aria-labelledby`) — not just a placeholder.
- This app has no validation errors today (no required fields, no client-side validation). If one is added: the error text needs `role="alert"` (or `aria-live="assertive"`) and the field needs `aria-invalid` + `aria-describedby` pointing at it, and the message must say what's wrong **and** how to fix it — not just "inválido"/"obrigatório".

### Dynamic content (4.1.3, 1.3.1)
- Purely decorative loading states get `aria-hidden="true"` (`ProfessionalCardSkeleton.vue` already does this) — anything that instead needs to be announced gets `role="status"`/`aria-live="polite"` (the results-count heading already has `aria-live="polite"`).
- A state change that's meaningful but not a full navigation (a failed fetch, in particular) should live inside `role="alert"` or `role="status"` so it's actually announced — check `HomeResultsGrid.vue`'s error state for this.

### Color and contrast (1.4.1, 1.4.3)
- Status never conveyed by color alone — pair it with an icon, text, or shape change. The favorite-toggle button already does this right (`aria-pressed` + a fill change on the heart icon, not just a border-color swap) — that's the pattern to match anywhere else a toggle exists.
- Flag any hardcoded color pair whose contrast you can't already vouch for from `DESIGN.md`'s palette, and list it for manual verification (contrast can't be reliably checked by reading markup — a real check needs the rendered page).

### Font sizes (1.4.4)
- This project's entire type scale is defined in raw `px` (the `@theme` tokens, every `text-[Npx]` and `clamp(Npx, …)` in the codebase) rather than `rem`/`em`. Note it, but **don't treat it as an automatic fix** — modern browsers reflow `px` text on zoom same as `rem`, so this is lower-priority than it used to be, and converting the whole fluid-type system is a deliberate, scoped decision, not something to do silently as a side effect of an accessibility pass. Flag it once in the report as a judgment call for the user, not per-occurrence.

### Reduced motion (2.3.3 best practice)
- New CSS animations need a `prefers-reduced-motion: reduce` counterpart. This project centralizes that in `main.css`'s existing `@media (prefers-reduced-motion: reduce) { … }` blocks (see `.btn-primary`, `.hero-orb`, `.skeleton`) — match that pattern (add the new selector to one of those blocks, or a new block) rather than mixing in Tailwind's `motion-safe:`/`motion-reduce:` variants, unless the animation is a one-off utility class with no dedicated component rule to attach to.

### Touch targets (2.5.8)
- Every interactive element at least 24×24 CSS px; primary actions (main CTAs) at least 44×44. Check the actual rendered size from the Tailwind size/padding classes, not just that *a* class is present.

### Not currently applicable (check anyway — flag if introduced)
- Destructive-action confirmation (3.3.4) — no delete/irreversible action exists yet.
- Format hints for constrained inputs (CPF/phone/date, etc.) — no such input exists yet.
- Single-key shortcuts, drag-and-drop keyboard alternative, pointer-cancellation — none of these patterns exist yet.

## Step 4 — Apply fixes (unless `REPORT_ONLY=true`)

Minimum change needed — don't refactor unrelated code. Priority order:
1. Missing accessible name (`aria-label`, label association) on an interactive element.
2. Missing/incorrect keyboard support (native element instead of a non-interactive one with a click handler; `tabindex`/`@keydown` if a native element genuinely isn't an option).
3. Missing focus management on `ProfessionalFiltersSheet.vue` (move focus in on open, return it on close) if found missing.
4. Missing `aria-hidden` on decorative SVGs / missing `alt` on images.
5. Missing `role="alert"`/`role="status"`/`aria-live` on dynamic content that should be announced.
6. Missing `aria-pressed`/`aria-expanded`/`aria-current` state sync.
7. Undersized touch targets — bump to the Tailwind size class that clears 24×24 (44×44 for primary actions).
8. Missing reduced-motion counterpart for a new animation.

Use the existing `sr-only` Tailwind utility for visually-hidden accessible text (already used in this project — `Hero.vue`'s search label, `FilterSelect.vue`'s `md:sr-only` label).

## Step 5 — Tests

Every component has a test file under `test/components/` and a 90% per-file coverage floor (see the `devmatch-patterns` skill's `testing.md`). So a fix applied here has somewhere to land:

- If the fix changes behaviour an assertion should pin (an added `aria-label`, a new `role`, focus moving into a dialog), add or update the assertion in that component's existing test file — query by role/label so the test fails if the accessible name regresses.
- Re-run `npm run test:coverage` after applying fixes; a markup change can drop a component below the floor.
- Don't add `axe-core`/`vitest-axe` as part of this command. That's a separate, deliberate decision (`testing.md` scopes when it's worth it) — flag it in the report instead.

## Rules

- Read the actual file before flagging anything in it — no guessing from a component's name or prior familiarity.
- Fix the minimum needed; don't use this pass as an excuse to refactor unrelated markup.
- Contrast and real rendered pixel sizes always go to "manual verification", never asserted as pass/fail from markup alone.
- `REPORT_ONLY=true` means exactly that — no file is written.
